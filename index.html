01 / Vault core

One file. Hardened.

The vault is deliberately small: strong derivation, authenticated encryption, predictable permissions, and a threat model that says exactly what it does not promise.

ENCRYPTED AT REST

Authenticated by design.

Tampered vault data fails to decrypt. A stolen file is still ciphertext without the master password.

ONE FILE / NO DATABASE

Portable without plaintext.

Carry one encrypted vault file instead of scattering secrets through config files, shell history, or notes.

BOUNDARY DECLARED

Honest about the threat.

It protects secrets at rest—not an already-compromised session, a keylogger, or someone watching you type.

02 / CLI surface

Every operation asks. Nothing lingers.

add reads a piped secret or prompts with hidden input. list shows labels, dates, and notes—never the secrets themselves. There is no background session waiting to be stolen.

NO UNLOCKED SESSION LEFT BEHIND

03 / TUI surface

Unlock once. Work locally.

The interactive terminal UI keeps the derived key in memory for the session only. Browse, search, reveal, copy, and generate through a focused operator surface.

KEY DISAPPEARS ON EXIT

04 / Threat model

Permissions are part of the write.

The vault directory is owner-only at 0700; the vault file is owner-only at 0600. CyberVault re-checks and reapplies those permissions on every save, not only during first creation.

SELF-HEALING PERMISSIONS

05 / Boot sequence

Put the vault on your machine.

One command downloads, verifies the checksum, and installs to ~/.local/bin.

>_ curl -fsSL https://raw.githubusercontent.com/cybercoretech/cybervault/main/install.sh | sh

Keysmith is optional and only needed for the TUI's ctrl+g / ctrl+p generate-in-place shortcuts.
